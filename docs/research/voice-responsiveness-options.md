# Research: Voice responsiveness and TTS options

## Summary
STT → LLM → TTS is a standard LiveKit architecture; waiting for an entire durable Codex operation before giving TTS any text is an application-specific serialization barrier, not a requirement of that architecture. First separate warm-STT latency, Codex/tool completion latency, and TTS first-audio latency; then stream eligible Codex final-answer text and audition OpenAI’s recommended `marin`/`cedar` before changing providers. Codex remains the sole reasoner, using the existing ChatGPT subscription authentication.

Scope: public primary-source research only. No inference, credentials, purchases, or application/service changes. Stack and 2,861 ms first-caption measurement are supplied observations, not independently reproduced. Current documentation is rolling; fetched pages include Sonic 3.6 and an ElevenLabs Inference retirement dated August 31, 2026. Treat these as the documentation snapshot retrieved, not evidence of what a previously installed package supported.

## Findings
1. **High — the bridge, not necessarily TTS, is the main avoidable wait.** LiveKit documents both cascaded STT–LLM–TTS and realtime speech-to-speech pipelines. Streaming generated text into synthesis allows stages to overlap. This application instead releases text only after the durable Codex result; a faster TTS cannot recover that preceding wait. The supplied 2,861 ms caption includes cold setup and speech-only upload: it is neither a steady-state streaming STT benchmark nor a TTS measurement. [LiveKit pipelines](https://docs.livekit.io/agents/models/pipelines/)

2. **OpenAI: try voices before replacing the model.** The current Speech guide explicitly says “For best quality, we recommend using `marin` or `cedar`”; `coral` is supported but is not that recommendation. It recommends `gpt-4o-mini-tts` for intelligent realtime applications and supports instructions controlling tone, intonation, emotion, accent, and speaking speed. Start with a restrained instruction such as “Clear, natural coding partner; conversational, concise; avoid exaggerated enthusiasm.” Faster delivery shortens speech duration, not necessarily inference time. There is no documented general quality-effort knob analogous to reasoning effort. The guide recommends WAV or PCM for fastest response times; PCM is 24 kHz, signed 16-bit little-endian. Audio can play before generation finishes. [OpenAI Speech guide](https://platform.openai.com/docs/guides/text-to-speech)

3. **Important distinction: streamed audio output is not streamed text input.** The version-tagged LiveKit OpenAI TTS implementation declares `TTSCapabilities(streaming=False)`, accepts a complete `input_text`, but uses `with_streaming_response.create` and emits received audio progressively. For `gpt-4o-mini-tts` it uses SSE; `tts-1`/`tts-1-hd` use audio streaming. Thus `streaming=False` does not mean “wait for the full audio file”: the pipeline must segment incremental text into synthesis requests. That tag defaults to MP3 and exposes `response_format`, `instructions`, and `speed` (default 1.0); confirm the local configuration before assuming these defaults apply. Prefer sentence/clause chunks over individual tokens to preserve prosody. [LiveKit OpenAI TTS source, Agents 1.5.12 tag](https://raw.githubusercontent.com/livekit/agents/livekit-agents%401.5.12/livekit-plugins/livekit-plugins-openai/livekit/plugins/openai/tts.py)

4. **Cartesia: true bidirectional streaming, with warm-connection support.** Current LiveKit documentation lists Sonic 3, 3.5, and 3.6; Sonic Turbo and Sonic 2 are deprecated in LiveKit Inference. Cartesia now calls `sonic-3.6` its fastest model and lists stable snapshot `sonic-3.6-2026-08-27`. Its product page advertises sub-90 ms latency: this is a vendor claim, not this app’s measured end-to-end latency or an independently verified quality ranking. Use a supported pinned snapshot for reproducibility, not a moving latest alias. WebSocket contexts accept incremental transcripts with `continue: true`, preserve prosody across inputs, and terminate with `continue: false`. Current LiveKit plugin documentation says it reuses an open WebSocket across turns and supports prewarming; verify the separately installed Cartesia plugin version before relying on this. [LiveKit Cartesia](https://docs.livekit.io/agents/models/tts/plugins/cartesia/), [current model](https://docs.cartesia.ai/build-with-cartesia/tts-models/latest), [advertised latency](https://www.cartesia.ai/sonic), [WebSocket contexts](https://docs.cartesia.ai/use-the-api/tts-websocket/contexts)

5. **ElevenLabs: Flash v2.5 is the documented low-latency candidate.** The latency guide recommends Flash and advertises approximately 75 ms **model inference only**, explicitly excluding end-to-end effects. It estimates WebSocket TTFB at 100–150 ms in North America/Europe/SE Asia and 150–200 ms in South/NE Asia; these too are vendor estimates. It acknowledges slightly lower quality than Multilingual v2. Bidirectional WebSockets fit incremental LLM text; HTTP streaming fits text already available. `auto_mode=true` handles generation triggers; otherwise chunk thresholds can stall short replies. LiveKit says explicitly setting a chunk schedule disables auto mode; allowed values are 50–500 characters, vendor default `[120,160,250,290]`. Current LiveKit documentation says ElevenLabs is retired from LiveKit Inference (August 31, 2026), **but remains supported through the provider plugin and a separate ElevenLabs account**. [ElevenLabs latency guide](https://elevenlabs.io/docs/eleven-api/guides/how-to/best-practices/latency-optimization.mdx), [LiveKit plugin](https://docs.livekit.io/agents/models/tts/plugins/elevenlabs/)

7. **High — streaming must not weaken durable tool-result guarantees.** Codex App Server exposes `item/agentMessage/delta`; `agentMessage.phase`, when present, distinguishes `commentary` and `final_answer`. `item/completed` is authoritative; `turn/completed` can mean completed, failed, or interrupted. Suggested design: keep the durable operation stream unchanged, and add an ephemeral speech stream keyed by thread/turn/item IDs, limited to eligible final-answer text. Never speak reasoning/tool logs; suppress replay duplicates and cancel queued audio on interruption. Release result-dependent sentences only after their relevant durable evidence is committed. If the bridge cannot establish that before operation completion, retain the gate for those claims: a final-answer delta is not proof of successful durable execution. Streaming still helps read-only replies or final narration after the tool-result barrier. Optional immediate acknowledgments must be deterministic and truthful (“Working on that”), not a second LLM or invented progress. Keep current ChatGPT auth; the app-server documents ChatGPT-managed authentication separately from API-key authentication. [Codex App Server protocol](https://developers.openai.com/codex/app-server/)

8. **High — preemptive generation is a later optimization for this coding agent.** Current LiveKit turn-tuning docs say preemptive LLM generation starts when a final transcript arrives, before turn confirmation; default enabled, speculative TTS default disabled, maximum speech duration 10 seconds, maximum retries 3. Cancellation/re-generation can waste compute and TTS charges. It does not make a per-utterance STT result arrive earlier. More importantly, canceling speculative narration does not undo a file edit or shell command. Do not enable speculative side-effecting Codex operations: require confirmed turns and existing approval/idempotency boundaries. Validate actual settings against installed 1.5.12 and the custom bridge rather than copying rolling examples blindly. [LiveKit turn tuning](https://docs.livekit.io/agents/logic/turns/tuning/)

## Small ordered plan
1. **Instrument first:** speech end → endpoint confirmation → STT request/first caption/final transcript → Codex first eligible final text → durable tool/operation completion → first TTS request/byte/frame → Flutter audible playback. Record cold first turn separately from warmed turns and compare p50/p95 on the same prompts. No current numbers establish TTS as the dominant delay.
2. **Warm STT/setup separately:** retain reusable clients/connections and pre-load VAD where supported; verify whether the per-utterance transport permits preconnection. Do not send paid synthetic warm-up requests. Parent correction from implemented and live-tested code: STT already streams voiced frames and returns pre-commit partials. One connection per utterance describes socket lifetime, not buffered transcription. Preconnection would reduce setup latency only; it must never upload idle audio.
3. **Unblock safe Codex final-text streaming** with the durability guard above. Keep Codex as sole reasoner. Acknowledge receipt promptly without implying success; do not trade correctness for speculative coding actions.
4. **Tune existing OpenAI TTS:** audition coral vs marin vs cedar, restrained instructions, modest speaking-rate changes, and PCM/WAV versus the actual configured format. Check sentence-buffer delays and warm HTTP reuse independently of STT warming. Do not assume provider-byte arrival equals audible client playback.
5. **Only if needed, authorize a small human A/B later:** compare pinned Cartesia Sonic and ElevenLabs Flash v2.5 through their supported plugins using identical coding phrases, abbreviations, paths, numbers, and short/long replies. Measure cold/warm first-audio and sentence continuity; score naturalness/intelligibility by listening. No audible-quality benchmark was performed here. Provider changes require separate billing/credentials and approval; none were provisioned.

**Not compatible with the present constraint:** replacing this with OpenAI Realtime or another native speech-to-speech conversational model may reduce pipeline stages, but introduces/replaces the conversational reasoner and therefore violates “Codex subscription ONLY reasoner.” TTS-only provider swaps do not.

## Parent repository verification

- `apps/voice/src/orchestrator_voice/worker.py`: `llm_node` yields only after `bridge.answer` completes. TTS construction specifies model/voice only.
- `apps/voice/src/orchestrator_voice/bridge.py`: `_poll` returns text only for a succeeded operation; default polling interval is 1 second.
- `apps/voice/src/orchestrator_voice/config.py`: VAD endpointing uses a 0.8-second minimum; preemptive generation/TTS are disabled. Do not blindly add this delay to VAD/STT durations: the SDK may overlap their timing.
- Installed OpenAI plugin 1.5.12 defaults to MP3 and uses streaming SSE audio for mini TTS; it still requires complete text per synthesis chunk.
- Private deployment configuration verified by printing only selected nonsecret fields: `gpt-4o-mini-tts`, voice `coral`. No settings changed for this research.
- Read-only journal sample: last eight successful voice control operations took 9,381; 4,156; 3,969; 12,698; 5,928; 5,717; 6,004; and 4,674 ms from acceptance to success. These include queue, Codex and tools; they exclude STT, polling after completion, TTS, and client playback. Mixed prompts/runtime generations, not a controlled benchmark or TTS latency measurement.
- `apps/control/src/codex.ts` currently collects completed agent messages and resolves at turn completion; it does not forward text deltas. Routing reasoning effort is not explicitly set here.
- `apps/control/src/service.ts` does not yet request shorter speakable replies for source-voice input. It supplies recent context to an already persistent Codex thread; repeated-context overhead is another profiling candidate, not a measured cause.
